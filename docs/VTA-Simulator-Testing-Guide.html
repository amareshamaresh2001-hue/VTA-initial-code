VTA-Simulator — Build, Run & Test Guide

A step-by-step manual for building the SystemC VTA simulator, running it on different inputs, and — most importantly — testing your own changes as you port vta.h / vta.cc (Vivado HLS) into SystemC.

Project: E:\Uni Siegen\PEP\VTA-Simulator-main  •  Platform: Windows 11 + VS Code + vcpkg

Read this first. There are only three actions you ever repeat: Build → Run → Check the output. Everything in this guide is a variation of those three. The hard one-time setup (compiler, libraries) is already done.

0. What you are actually doing

The files vta.h and vta.cc in the PEP folder are the original VTA hardware design written in Vivado HLS C++ (they use ap_int, hls::stream, and #pragma HLS — Xilinx-specific). Your job is to re-express that same hardware behaviour as SystemC inside this simulator project, which already provides the matching module skeletons.

HLS function in vta.ccbecomes this SystemC module in the projectfiles
fetch()Fetcherinclude/simulation/fetcher.h, src/simulation/fetcher.cpp
load()LoadModuleinclude/simulation/load_module.h, src/simulation/load_module.cpp
compute()ComputeModuleinclude/simulation/compute_module.h, src/simulation/compute_module.cpp
store()StoreModuleinclude/simulation/store_module.h, src/simulation/store_module.cpp
vta() (wrapper)VTA (wires everything together)include/simulation/vta.h, src/simulation/vta.cpp

So "transforming and testing" means: edit the SystemC module files, rebuild, run the simulator, and confirm the output still makes sense (e.g. all layers still finish, timings are reasonable).

2. The core cycle: Build → Run → Check

ABuild (compile the code)

In VS Code: press Ctrl+Shift+P → type CMake: Build → Enter. (If asked for a preset, choose vcpkg.) A clean build of everything is CMake: Clean Rebuild.

In a terminal (from the project folder):

.\build.cmd

Success looks like ===== BUILD OK ===== or, if nothing changed, ninja: no work to do. Either means you are good to run.

If the build fails, the terminal shows the file and line number of the first error (e.g. compute_module.cpp(42): error C2065: ...). Fix that line, build again. Always fix the first error first — later ones are often caused by it.

BRun (execute the simulation)

In VS Code: press F5 and choose “Run VTA Simulator (Ninja build)”. Output appears in the terminal panel.

In a terminal:

.\build\my_systemc.exe
Why it just works: the two required DLLs (libzmq-mt-4_3_5.dll and nlohmann_json_schema_validator.dll) are copied next to the .exe in build\. If you ever delete build\ and rebuild, re-copy them from vcpkg\installed\x64-windows\bin\ (or just run from a terminal that has that folder on its PATH).

CCheck the output

The simulator prints one line per network layer:

211040 ns      ---------------------------- FINISH LAYER 0 ----------------------------
758676 ns      ---------------------------- FINISH LAYER 1 ----------------------------
...
58021575 ns    ---------------------------- FINISH LAYER 102 ---------------------------

The number is the simulated hardware time in nanoseconds at which that layer finished. The difference between two consecutive lines is that layer's latency. This is the result you compare before and after a change.

3. Testing with different inputs

The "input" is chosen in config/config.json. The most important field is model_name.

Switch the model

  1. Open config/config.json.
  2. Change "model_name" to one of: resnet_18, resnet_34, resnet_50, resnet_101.
  3. Save, then Run again (no rebuild needed — config is read at runtime).

Smaller models (resnet_18) have fewer layers and finish faster — handy for quick tests.

What every config field means

FieldMeaning / effect on the simulation
model_nameWhich data/models/<name>.csv to simulate.
granulatity"layer" or "block" — how instructions are grouped/reported.
en_cacheEnable the on-chip cache model (changes memory timing).
en_prefetchEnable prefetching.
en_ddr_lockModel DRAM access locking/contention.
max_cache_mem_sizeCache size budget used by the cache model.
nr_load_pipeline / nr_compute_pipeline / nr_store_pipelineHow many parallel pipelines each stage has (more = more parallelism).
load_cycles / load_weigts_cycles / store_cyclesLatency (in clock cycles) charged per load / weight-load / store operation. These directly drive the ns numbers.
Good test idea: run the same model twice — once with en_cache=false and once with en_cache=true — and compare the layer timings. This shows the cache model is having an effect, and is a clean way to demonstrate the simulator to a supervisor.

Make a tiny test model (fast iteration)

The full ResNet CSVs are large. To test a change quickly, copy a model and keep only the first few rows:

# PowerShell — create a 1-layer mini model from resnet_18
$src = "data\models\resnet_18.csv"
$dst = "data\models\mini.csv"
Get-Content $src -TotalCount 60 | Set-Content $dst   # header + first ~59 instruction rows

Then set "model_name": "mini" in the config. It runs in a fraction of a second, so you can build-run-check many times while debugging a module.

4. The transformation workflow (porting HLS → SystemC)

This is the loop you will repeat while moving logic from vta.cc into the SystemC modules.

1Decide which module you are changing

Use the mapping table in section 0. E.g. porting the HLS compute() body → edit include/simulation/compute_module.h and src/simulation/compute_module.cpp.

2Edit the SystemC code

Translate HLS idioms to SystemC equivalents:

HLS (vta.cc)SystemC equivalent in this project
hls::stream<T> (FIFO)a Queue module connected by vld/rdy/data/end signals
ap_int<N> / ap_uint<N>sc_int<N> / sc_uint<N>
#pragma HLS PIPELINE etc.(ignore — pragmas are hardware-synthesis hints, not needed in simulation)
function called once, returnsmodule process driven by sc_events, reacting over simulated time
dependence queues (l2g, g2l, s2g, g2s)the l2c / c2l / s2c / c2s Queues wired in vta.cpp

3If you ADD a new .cpp file, register it in CMakeLists

The build only compiles files listed in CMakeLists.txt. Open it and add your new file inside the add_executable(my_systemc ...) list:

add_executable(my_systemc
    main.cpp
    src/utilities/utilities.cpp
    ...
    src/simulation/vta.cpp
    src/simulation/arm.cpp
    src/simulation/my_new_file.cpp      <-- add your new .cpp here
)
Common mistake: creating a new .cpp but forgetting to add it here. Symptom: unresolved external symbol (linker error) at the end of the build. Fix = add the file to the list above. (Header-only changes to existing .h files do not need a CMakeLists edit.)

After editing CMakeLists.txt, run CMake: Configure once (VS Code does this automatically on save), then build.

4Rebuild and run

Build (section 2A) → Run (section 2B). Watch for compile errors first, then runtime behaviour.

5Verify the result (regression test)

Since the project has no automated test suite, you test by comparing output against a known-good baseline:

# 1) BEFORE your change — capture a baseline (do this once, on the working version):
.\build\my_systemc.exe > baseline.txt

# 2) AFTER your change — capture the new output:
.\build\my_systemc.exe > current.txt

# 3) Compare them:
Compare-Object (Get-Content baseline.txt) (Get-Content current.txt)

Interpretation:

  • No differences → your change preserved behaviour (good for a refactor that shouldn't change results).
  • Timing numbers changed but all 0…N layers still finish → expected if your change affects latency; check the new numbers are sensible.
  • Fewer layers, a crash, or it hangs → a regression; your change broke something. Re-check the edited module.

5. A repeatable test checklist

Run through this every time you finish a transformation step:

#CheckPass criteria
1It buildsBUILD OK / exit code 0, no errors
2It runs without crashingProcess exits with code 0
3All layers finishYou see FINISH LAYER 0 … up to the last layer of the model
4Timings are monotonic & sensibleThe ns values increase; no zero/negative/garbage values

6. Troubleshooting

SymptomCause & fix
unresolved external symbol at link timeA .cpp isn't in CMakeLists.txt (section 4, step 3), or a function is declared but not defined.
App can't start: ...dll was not foundRun from build\ (DLLs are there), or add vcpkg\installed\x64-windows\bin to PATH, or re-copy the two DLLs into build\.
Build error iostream: no include path setThe compiler environment isn't loaded. Use build.cmd (it calls vcvars64) or build via VS Code's CMake Tools.
Error opening file: ...csv / model not foundThe CSV must be at data/models/<model_name>.csv. Check the name in config.json matches a file there.
CMake can't find SystemC / a libraryThe vcpkg preset isn't selected. In VS Code choose the vcpkg configure preset; or re-run build.cmd.
Changed config but output is identicalYou may have edited a copy. Confirm you saved config/config.json in the project root.
